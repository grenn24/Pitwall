Agentic IDE

A desktop app for developers who orchestrate AI agents instead of typing most of the code. This revision fixes the MVP target to Windows, settles how agents share state, settles concurrency, and corrects an auth model that could not have shipped as written.

What changed since v0.1

§4 · Rule 1
Agents share state, they don't message. Restated as an architecture rule with the four artifacts that carry intent, plus a new Rule 4: the run engine owns handoff, not the agents.
§5 · new
Concurrency model added. Sequential within a ticket, parallel across tickets, capped at three. Closes the laptop-sleep question.
§5 · conflicts
Merge conflicts settled: the orchestrator decides, the AI recommends. Declared file scope prevents most; the rest halt both tickets and wait for a human accept. New terminology split — orchestrator is the person, run engine is the scheduler.
§6 · Windows
MVP platform fixed to Windows. Electron over Tauri. Docker means WSL2, and that is now a first-run feature rather than a footnote.
§7 · auth
Correction. The v0.1 PR flow required a GitHub App private key on the user's machine. It can't ship. Replaced with device flow, and the self-approve step is cut from v0.
§8 · scope
"Deploy" split explicitly into local preview deploys (we build) and production status display (we read). No change in direction, just no longer ambiguous.
§11 · reversed
v0 ships the three-role team, not one agent. The role split is architecture rather than a feature, so a single-agent v0 would teach us nothing and then be rewritten. Cross-ticket parallelism is what gets deferred instead.
§4 · skills
Skills specified as the per-role extension point. They live in the repo, attach to one role, and cannot widen that role's permissions. Pulled from an existing public registry rather than one we build — vendored, hash-pinned, and reviewed before install.
§12 · cuts
The validate-before-building week is removed, and pricing is deferred outright — not a question until the MVP is in someone else's hands.
§ 01Unchanged

What it is

A desktop app for developers who orchestrate AI agents instead of typing most of the code. You write tickets. A team of role-based agents plans, writes tests, writes code, and reviews. You approve or send it back.

Not an editor. It embeds Monaco or CodeMirror. We do not build a text editor, language server, or debugger.

Not no-code. Code is still the artifact. Review is the interface.

§ 02Unchanged

Who it's for

Individual developers first. They install things themselves, so there is no sales motion to build.

The team view — fleet of agents, cost per run, approved capabilities, audit trail — comes later, and is where higher pricing lives.

§ 03Revised

Core loop

  1. Connect a repo
  2. Pick your agent team (default: 3 agents)
  3. Write a ticket
  4. Agents produce a plan. The user approves the plan
  5. Tests are written first, from the ticket
  6. Coder writes code on its own branch
  7. Preview URL and isolated database spin up
  8. Reviewer runs the tests and opens the app
  9. User reviews: screenshots, test results, diff
  10. Approve → merge. Or send back with a comment
  11. Branch, containers and preview are torn down

While a run is going, the user can pause an agent, open and edit the code directly, chat with one agent, or reorder tickets.

Revised — step 10

"Approve" in v0 means merge from inside the app, not a GitHub PR approval. The identity trick that made in-app PR approval work in v0.1 needs a backend we are not building yet. See §7.

§ 04Revised

Agents and roles

A role is a bundle: instructions, tools, skills, permissions. Ship a predefined set. Users can edit roles and choose how many agents they run.

RoleDoesCannot
DesignerUI decisions, layout, statesTouch backend
CoderImplementationApprove its own work
ReviewerRuns tests, opens the app, judges against the ticketWrite code

Do not make people configure a team before their first result. Ship the default. Let them edit after they have seen it work.

Skills — the per-role extension point New

Of the four things in a role, instructions and permissions are ours and tools are the platform's. Skills are the developer's. A skill is a folder of instructions plus optional scripts, loaded on demand by name and description, and it is how a team teaches an agent something we could never ship in the box.

Three properties make this work:

01Per roleA skill attaches to one role, not to the whole team. Designer gets the design system, Coder gets the repo's migration conventions, Reviewer gets the acceptance checklist. Loading all three into all three is how you get an agent that reviews its own work in its own vocabulary.
02In the repoSkills live in a versioned directory in the project, not in the user's app settings. They ship with the code, review through pull requests, and every teammate gets them by cloning. A skill that lives on one laptop is a private habit, not a team convention.
03Under permissionsA skill cannot widen the role that loads it. Give the Designer a database migration skill and it still cannot touch the backend — the tool layer refuses. Skills add knowledge, never capability.

Pulling skills from a registry New

Developers should not have to write every skill themselves, and a public directory of them already exists — skills.sh distributes GitHub-backed skills under an owner/repo namespace, installed with npx skills add, across twenty-odd agent platforms.

Consume that ecosystem, do not build one. Same reasoning as keeping GitHub in §7 and refusing to write an e2e framework in §6: a registry is a network-effects business, we would lose it, and the skills we care about are already there.

Installing means vendoring into the repo, never into a global cache. The skill is copied into the project's skills directory, attached to exactly one role, and pinned in a lockfile by source, ref and content hash. It arrives as a commit.

Why vendored and not global

A global install breaks the property that makes skills useful in the first place — one developer's Reviewer would behave differently from another's, with nothing in the repo to explain why. Vendored, a skill goes through the team's normal pull request review, CODEOWNERS applies to it, and git log says when the Coder's behaviour changed and who changed it.

Trust is the hard part

A skill is instructions plus executable scripts, running with a role's tools, on a developer's machine, in a repo with a GitHub token in scope. Installing a third-party skill is running third-party code, and the instructions half is prompt injection wearing a lower-privilege costume. Four rules, none optional:

  • Show it before installing. Files, scripts, tools referenced, network access requested. No blind install
  • Pin to a content hash, never a moving ref. Updates are a diff someone approves, never silent
  • Permissions still bind. A skill can never widen the role that loads it. A skill declaring a tool its role lacks is a warning at install time, not an escalation prompt
  • It lands as a commit. Whatever review the team already applies to code applies to this
v0 stance

v0 ships the mechanism, not the storefront. Add a skill by owner/repo reference, review what is in it, attach it to a role, and it is vendored and locked. Browsing, trending and search inside the app are v1 — they are a UI over the same mechanism, and the mechanism is the part that is expensive to retrofit.

There is still no skill editor. Writing one means committing a folder.

Rule 1 — Agents share state, they do not message each other

The choice is not "isolated versus communicating." It is message passing versus shared state, and we want shared state.

Message passing fails because every hop is a paraphrase. Designer summarizes the ticket for Coder, Coder summarizes its work for Reviewer, and by the third hop nobody is reading the original ticket. Errors compound and context grows without bound. Full isolation fails differently: agents duplicate work and make contradictory assumptions with no way to notice.

Shared state avoids both, because every agent reads the same ground truth on every turn and nothing is summarized in transit. Communication in this system is four artifacts, not a chat log:

01Ticket docSpec, constraints, decisions. Append-only, sections owned by role, every write attributed and timestamped.
02The branchThe diff is how Coder talks to Reviewer.
03Test outputPass or fail is how Reviewer answers back.
04The humanA blocked agent escalates up, never sideways to another agent.

Rule 2 — The reviewer must act, not read

A reviewer that only reads the diff approves almost anything: same model, same blind spots. It needs independent ground truth — run the test suite, open the running app with Playwright, check against the written ticket.

Rule 3 — Tests come before code

If the coder writes code and then tests, the tests describe the bug too. They always pass, and they are useless. Tests are generated from the ticket, before implementation.

Rule 4 — The run engine owns handoff New

Agents do not decide when they are done. Handoff is a state machine transition owned by the run engine — spec_ready → tests_written → code_complete → review_passed — triggered by artifacts existing and checks passing.

Why this rule exists

If an agent can declare itself finished and summon the next one, you have rebuilt message passing with extra steps, and Rule 1 quietly stops holding.

Terminology

The orchestrator is the person — this is a product for developers who orchestrate agents. The run engine is the deterministic scheduler that moves tickets between states and holds no opinions. Keeping the two words apart matters in §5, where the orchestrator decides and the run engine only enforces.

§ 05New section

Concurrency model

Sequential and parallel are two different axes. Conflating them is what makes multi-agent setups feel slow and expensive for no gain.

Within one ticket: sequential

Tests → code → review is a hard data dependency. You cannot write code against tests that do not exist. Running these stages concurrently means agents idle while they wait, which produces exactly the 3× cost and worse wall-clock time v0.1 predicted. The one genuine overlap is Designer running alongside test-writing, since both consume only the ticket.

Across tickets: parallel

This is where the product is. Three tickets, three worktrees, three container pairs, one human reviewing whichever finishes first.

Consequence

Cross-ticket parallelism is the only reason per-branch isolation needs to exist. With one ticket at a time, the database-per-branch design is dead weight. Build isolation and parallelism together, or neither.

The cap

Two to three concurrent tickets. Each one is two containers plus a language server plus a test runner. Past three, Docker Desktop is eating 12 GB and the user blames our app, not their laptop. Show running cost in the UI so the ceiling is legible before it is hit.

How to build it

A job queue with stateless workers keyed off a ticket record. Agents hold no memory between turns; everything they know comes from the ticket doc and the worktree. Sequential versus parallel is then a scheduler setting rather than a rewrite — which matters, because v0 ships one agent and this question does not bite until v1.

Laptop sleep

Every state machine transition is a durable checkpoint. On sleep the run halts at its last committed checkpoint and the worktree stays on disk; on wake it resumes from there. Nothing is lost, a run just takes longer than the user expected. Say that plainly in the UI rather than pretending the run survived.

Merge conflicts between tickets Decided

Prevention first: each ticket declares its expected file scope during planning, and the run engine refuses to schedule two tickets whose declared scopes overlap, queueing the second instead. That removes most conflicts before they exist.

For the ones that still happen, the orchestrator decides and the AI recommends. No agent commits a conflict resolution on its own — agents resolving each other's conflicts is Rule 1 violated in the worst possible place.

01HaltThe run engine stops both tickets at their last checkpoint. Neither branch advances while the conflict is open.
02BriefSurface the conflicting hunks alongside both ticket docs, so the orchestrator sees the two intents, not just the two diffs.
03RecommendAn agent drafts a proposed resolution and states its reasoning. It is a suggestion in the review screen, never a commit.
04DecideThe orchestrator accepts, edits, or rejects. Only that decision writes to the branch.
05ResumeBoth tickets restart from their checkpoints with the resolution applied.

The recommendation is worth building because the alternative — dumping a raw conflict on the user with no context — is the moment the product stops feeling like it is doing the work. But the accept step is not optional, and it is not a setting.

§ 06Revised

Architecture decisions

Windows desktop, Electron

The MVP target is a Windows app. Electron over Tauri: Monaco, simple-git, dockerode and node-pty are all Node-native and we will use every one of them. Tauri's smaller binary is not worth rebuilding that layer in Rust.

Runs on the user's laptop

  • No server bill for us
  • Company code never leaves the machine — a real enterprise selling point
  • Known downside: close the laptop and agents stop (see §5)
  • An optional cloud runner is a later addition, same product

Docker on Windows means WSL2

Docker Desktop requires it, and this is the hardest step in onboarding. A repo living on C:\ and mounted into a Linux container gets slow filesystem access and unreliable file watching, so hot reload in preview containers will be flaky.

Decision

Agent worktrees are cloned inside the WSL2 filesystem, not on the Windows drive. First run detects WSL2 and Docker and walks the user through installing whatever is missing. This is an MVP feature with real UI, not a line in the README.

Two more Windows details that will otherwise cost a day each: set core.longpaths, because git worktrees hit the 260-character path limit quickly; and set core.autocrlf explicitly, or every agent diff arrives as pure line-ending noise.

Per-branch isolation

Each ticket gets its own git branch, app container, and database container (Docker plus a seed file).

Separate databases because parallel agents on a shared one corrupt each other. Agent A adds a column and Agent B's code breaks. Agent B wipes the users table and Agent A's preview goes blank. Docker per branch works with any Postgres or MySQL, so no vendor lock; fast paths for Neon and Supabase branching can come later.

Testing

Do not build integrations per framework. Run whatever test command the project already has. Jest, Vitest and Playwright all print pass/fail and exit with a code. Read that.

Do not build an e2e framework. Playwright and Maestro exist and have years of work in them. What we build is the viewer: screenshots, video on failure, and test output in the review screen. Playwright already records all of it.

§ 07Corrected

Git and GitHub

Keep GitHub and GitLab. They are the standard and teams will not leave them.

  • One branch per ticket
  • The agent commits as it works
  • On merge, squash into one clean commit named after the ticket — never show the user 30 messy agent commits
  • Author is the agent, co-author is the user, so git blame still means something
Correction to v0.1

v0.1 said we ship a GitHub App that opens the PR while the user approves it with their own account. Minting a GitHub App installation token requires signing a JWT with the App's private key. That key cannot ship inside a Windows app — anyone can extract it and gain write access to every repo the App is installed on.

The auth model that works with no backend

GitHub App device flow. It yields user-to-server tokens with no client secret on the machine. We keep fine-grained per-repo permissions, org admin control over which repos the App can touch, and higher rate limits than a personal token. Through the API we can then open the PR, read the diff, comment on lines, merge, and read CI status.

What we lose: the PR is now authored by the user, so the user cannot approve it — same identity, and GitHub forbids self-approval. For v0 that is fine. Drop the approve step and merge directly; approval only matters where branch protection requires it.

When the App identity genuinely needs to be the PR author, that is the moment a small token-minting service earns its place. Plan for it, do not build it yet.

Unchanged and still a selling point

Never bypass branch protection or CODEOWNERS. The team's existing rules keep applying.

§ 08Clarified

Deployment

"Deploy" is two features. The MVP ships both, and they share almost nothing.

 Preview deploysProduction deploys
We build itYesNo
WhereContainers on the laptop, per branchTheir Vercel, their Actions, their pipeline
WhyMandatory — the reviewer cannot open the app otherwiseAlready solved, and better than we would
LifetimeTorn down on mergeNot ours
Our surfacePreview URL, seeded DB, teardownRead status from the API and display it

Production status is read-only: Merged → Deploying → Live, pulled from the GitHub deployments and checks API. Cheap to build, and it makes the loop feel finished.

Rejected

A "deploy anywhere" abstraction. Every platform differs, the abstraction leaks, and it means competing with Vercel while paying server bills.

§ 09Recommendation added

UI direction

Futuristic, modern, minimal. Dark and light modes.

Two candidates for the main screen. Board — columns are stages, cards are tickets, and with roles the columns mean something. Inbox — only shows agents that are blocked, failed, or waiting for review, and everything else stays quiet.

Recommendation

Ship the inbox as the default view and the board as a secondary map. With a cap of three concurrent tickets (§5), a board is nearly empty and the inbox is nearly always the right screen. The board earns its place at the team tier, where a fleet actually needs a map.

§ 10Extended

Explicitly out of scope

Listed so scope creep has something to bounce off.

  • A text editor, language server, or debugger
  • Our own e2e test framework
  • Mobile app testing — web first, add it if customers ask
  • Production deployment
  • A universal "deploy anywhere" layer
  • Replacing GitHub or GitLab
  • Building a skills registry. Consume the public one (§4). A registry is a network-effects business and we would lose it
  • Any backend service in v0. The moment one exists we own uptime, secrets and a bill. It comes when §7 forces it and not before
  • macOS and Linux builds until the Windows loop feels good. Electron makes the port cheap later; the WSL2 work does not transfer, so doing all three now triples the environment surface for no extra learning
§ 11Revised

v0 — the thinnest version that is still the real product

v0.1 said one agent. That is reversed. The role split is architecture, not a feature: Rule 1's shared ticket doc, Rule 4's handoff engine, and role-scoped permissions all have to exist before anyone can tell whether the design works. Ship a single agent and v0 teaches you nothing about the thing this product actually is, then gets rewritten.

So v0 stays thin where thin is cheap — one ticket, no configuration, no fleet view — and goes full depth on the one axis the whole premise rests on.

01SetupWindows app installs, detects WSL2 and Docker, guides the user through what is missing
02ConnectOne repo, connected by GitHub device flow
03TicketOne ticket at a time, written by the user
04TeamThe default three roles — Designer, Coder, Reviewer — running the sequential pipeline from §5
05SkillsInstalled from the public registry by owner/repo, vendored and hash-pinned into the repo, attached per role and scoped by that role's permissions. No browse UI, no editor
06Shared docOne ticket document all three read and write. No inter-agent messaging anywhere in the codebase
07Run engineThe state machine owns every handoff, with durable checkpoints
08TestWritten first, from the ticket
09EnvironmentBranch, preview URL, seeded database container
10ReviewDiff, test output and screenshots in one screen
11ShipPR opened and merged from inside the app; production status read back from GitHub

Deferred to v1, deliberately

  • Cross-ticket parallelism. One ticket at a time in v0
  • Team configuration. The three roles are fixed and not editable — though their skills are, by committing a folder (§4)
  • Board view. Inbox only (§9)
  • PR approval step. Merge directly (§7)
  • Cloud runner
Why this costs less than it sounds

Multi-agent within a ticket is nearly free on infrastructure. The three roles run sequentially, so they share one worktree, one app container and one database container. Container count is driven by concurrent tickets, not by agent count.

The expensive half of multi-agent is cross-ticket parallelism — and that is exactly the half v0 defers. What v0 buys with the extra tokens is the only thing worth learning early: whether the shared-document design holds up when three roles depend on it.

Done means

A developer installs the app on a clean Windows machine, connects a repo, writes one ticket, watches three role agents take it from spec to merged PR, and never leaves the app or opens a terminal. Every requirement above exists to serve that sentence.

§ 12Updated

Open questions

Closed in v0.2 Board, inbox, or both? Inbox by default, board as a secondary map. Revisit at the team tier.
Closed in v0.2 Cap on concurrent agents? Three concurrent tickets, sequential within each. Running cost shown in the UI.
Closed in v0.2 What happens when the laptop sleeps? The run halts at its last durable checkpoint and resumes on wake. Told plainly, not hidden.
Closed in v0.2 Who resolves merge conflicts between two agents? The orchestrator decides; the AI recommends. Declared file scope prevents most conflicts, the run engine halts both tickets on the rest, an agent drafts a resolution, and only the orchestrator's accept writes to the branch (§5).
Deferred Pricing: per seat, per agent run, or per month? Not a question until the MVP exists. Revisit once v0 is in someone else's hands and we know what they use it for. One thing to carry forward: the laptop-runs-everything decision removes our compute cost, which will make per-run pricing hard to justify to a customer already paying their own model bill.
Still open Why doesn't GitHub or Cursor just ship this as a feature? Still needs an honest answer. Best candidate so far: this product's centre is the review and isolation loop rather than the editor, and neither company wants to own containers on a customer's laptop. That is an argument, not yet evidence.
