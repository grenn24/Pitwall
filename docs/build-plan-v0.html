Build Plan

Nine milestones from empty repo to a merged PR, ordered by risk rather than by feature. Each one ends in something you can run and a claim you can falsify. Scope is fixed by §11 of the spec: one repo, one ticket at a time, three fixed roles.

Done Not done
BEFORE M0

Settle this before writing anything

The repo lives in the WSL2 filesystem and the containers run in WSL2. So where does the agent process run?

If it runs on Windows, every file read, every edit and every git call crosses the WSL boundary. That is the slow path, and it is the same boundary that makes file watching unreliable. If it runs inside WSL2, the Electron UI on Windows becomes a client talking to a headless run engine over a local socket.

Recommendation

Build the split from day one: Electron UI on Windows, run engine daemon inside WSL2, one process boundary between them. Let M0 confirm the performance case, but put the boundary in the architecture immediately.

Introducing a process boundary later means touching every call site in the engine. Building against one from the start costs a week now and is the difference between a macOS port later being a packaging job and a rewrite.

Measured · 27 Aug 2026

Environment probe: 354 ms, five checks. Blobless clone of facebook/react: 7.5 s. Worktree add on that repo: 338 ms. Teardown: 154 ms.

Two detection traps found on real hardware, both now handled: wsl.exe emits UTF-16LE for management commands but UTF-8 for in-distro output, and docker can resolve on the Windows PATH to a non-executable stub, so Docker must be probed from inside the target distro.

M2The run engine, with no intelligence in it1 week

Stub agents that emit canned output. The state machine, the ticket doc and the permission layer all exist and are fully exercised before a single model call.

De-risksResumability and Rule 4 — the two things that are near-impossible to retrofit, and trivially testable while nothing is stochastic.
Build
  • SQLite store for tickets, run state and checkpoints
  • States and transitions, with a durable checkpoint written at each
  • Ticket doc as a versioned file: append-only, sections owned by role, every write attributed
  • Role permissions enforced at the tool layer, not in prompts
Exit criteria
  • Kill the app mid-run, reopen it, the run resumes from its checkpoint
  • Sleep the laptop mid-run — same result
  • A stub agent reaching for a tool outside its role is refused by the tool layer
  • The full happy path runs end to end with zero model calls

ORDER

Why this order

Three rules produced the sequence, and each one inverts the instinct to build the interesting part first.

Environment before intelligence. The genuinely novel risk in this product is not the agents — it is running two containers and a git worktree on a Windows laptop through WSL2 without the experience being miserable. M0 answers that in week one, while pivoting is still cheap.

Engine before agents. Checkpointing, permissions and handoff are deterministic problems. Test them against stubs where a failure means a bug, not a bad sample. Once model calls are in the loop, every test is flaky and every diagnosis is a guess.

One agent before three. M3 through M5 add roles one at a time so that when quality drops you know which role did it. Going straight to three means debugging a system where every variable moved at once.

CUTS

Cut lines, decided in advance

Decide these now, while it is cheap, rather than in week nine when it is emotional.

Cut if late

  • The Designer role (M6). Ship two roles. Coder and Reviewer alone still demonstrate the premise
  • Production status display (M8). Pleasant, not load-bearing
  • Video on failure (M5). Screenshots carry most of the value
  • Monaco embedding. "Open the code directly" can wait for v1
  • Registry install (M3). Fall back to skills committed by hand — the loader and the per-role scoping are what matter, the fetch is convenience

Never cut

  • Tool-layer permissions (M2). Retrofitting a security boundary is how you ship one that does not hold
  • Resumability (M2). A laptop product that loses work on sleep has one bug report, repeated forever
  • Reviewer ground truth (M5). Without it the product is a diff viewer with extra token spend
  • Tests failing before implementation (M4). The proof that Rule 3 is real
Not in this plan

Cross-ticket parallelism, the cloud runner, GitLab, macOS and Linux builds, the team tier, and pricing. All deferred by the spec, and all cheaper to add once the single-ticket loop is solid.
